# 5. Where the project stands, and what comes next

*Last updated 2026-11-16.*

## Current stage

**Plain.** We have a working system that answers questions about a ball after it has left the camera's view:
- **Fix A:** a written record outside the model, with a calculator that extends each ball's path.
- **Fix B:** distances in the sentence the model reads.
- **Fix C:** a change-aware rule for balls that stop, are moved or turn.
- **Zoomed look:** a second, closer look that measures each ball more precisely.
- **Look placement:** the rule "with few looks, zoom on the last moment each ball was seen".

On fresh twin videos, twin accuracy went from 5% (model alone) to about 67% (fixes A + B + C) and about 75% (with zoomed looks). This repository rebuilds all of it.

**Technical.**
- Settled: blocks 0–7 of [02_MODEL_STRUCTURE.md](02_MODEL_STRUCTURE.md).
- Last confirmed result: `last_each2 − fixed2` = +4.5 [+1.3, +7.8] on eval13 (round 9), the third set in a row.

## Next steps

### 1. Agent component: in progress
- **What holds.** Choosing where to zoom from the system's own estimate is a planner that calls a zoom tool (active perception). It works when looks are scarce.
- **Not supported yet.** A closed loop (look, read, then decide where to look next) has added about +1 in both simulation and real looks.
- **Candidate next test.** After a detected change of motion, decide whether the ball is standing still or still moving. A perfect version of this check would add about +4 to +6.6 points. A simple automatic version is 5–10 points worse than rule C, so the real check must beat rule C's own test.
- Pass rules are written before running, as for every round.

### 2. Improve the model itself (professor's comment)
- **Plain.** Everything that works so far sits *outside* the language model: the measuring part, the record and the calculator. The professor asked us to also make the model itself better at this, not only to wrap it in tools.
- **Possible directions, not yet researched:**
  - train the model to keep and update an internal object state;
  - change how it represents time and position across frames;
  - distil the calculator's behaviour into the model.
- Earlier attempts inside the model failed (NowRoPE, shared-trajectory supervision, memory tokens; see [06_HISTORY.md](06_HISTORY.md)). The new attempt should start from why those failed.

### 3. Real videos (professor's comment)
- **Plain.** All results so far are on simulated videos with three balls. We need to run the current system on real data, for example **Beyond3D**, to see whether it holds outside simulation.
- **Not yet researched:**
  - what format and labels that data has;
  - how its questions map to ours;
  - whether the measuring part needs retraining on real images.
- On real video only answer accuracy can be checked, not per-frame position error, unless the data has object positions.

### 4. Open questions carried over
- **Cost on edge hardware.** The zoomed look is one extra pass of the image encoder per frame: 1.3× slower at 448 than at 224 on an A100. On an edge chip this is untested.
- **Rule C vs IMM.** With estimated positions, rule C and the usual tracking method (IMM) are level (+1.0, range −1.8 to +3.7), so the "fake turns" explanation stays untested.
